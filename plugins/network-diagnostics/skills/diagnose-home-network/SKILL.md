# Diagnose a home network

Use the bundled macOS script for repeatable measurements. Keep measured facts,
inferences, and unverified possibilities separate throughout the diagnosis.

## Safety boundary

- Use only the bundled scripts and macOS system commands they invoke.
- Never run this workflow with `sudo` or as root. Do not install packages.
- Keep the fixed destinations: the detected router, `1.1.1.1`, `8.8.8.8`,
  `example.com`, Cloudflare's official download endpoint, and the server chosen
  by Apple's `networkQuality`.
- Never upload user files. The throughput and networkQuality tests transfer
  generated test payloads only.
- Do not add public-IP, ASN, or ISP-identification services without separate
  user consent.
- Treat missing privileged Wi-Fi fields as unmeasured. Never elevate merely to
  obtain RSSI or noise.
- Do not put secrets, addresses, account numbers, or an SSID in the label.

## Measure

1. Run the no-network plan from the user's intended working directory:

   ```bash
   python3 <skill-dir>/scripts/network_diagnostics.py <label>
   ```

2. Show the plan to the user before a traffic-heavy run. It states the fixed
   destinations and fixed download volume; Apple controls the additional
   dynamic traffic generated by `networkQuality`.
3. If the user already explicitly asked to execute the measurements, run the
   full test without asking again. Otherwise obtain confirmation, then run:

   ```bash
   python3 <skill-dir>/scripts/network_diagnostics.py <label> --run
   ```

4. Keep the generated JSON in the current directory's `results/`. The script
   creates it with user-only permissions and does not store hostname, SSID,
   BSSID, MAC address, or the full global IPv6 address.
5. For a deliberately lighter partial test, use `--skip-throughput` or
   `--skip-network-quality`. Mark skipped sections as unmeasured; do not use a
   partial run for a final bottleneck conclusion.
6. Repeat with a new label and otherwise identical arguments after each change.
   Compare two result files with:

   ```bash
   python3 <skill-dir>/scripts/compare_results.py <before.json> <after.json>
   ```

Read [interpretation.md](references/interpretation.md) before diagnosing the
result.

## Diagnose

1. Check section errors and skipped measurements first. Do not turn nulls,
   timeouts, or blocked probes into evidence.
2. Quantify the strongest supported bottleneck:
   - Wi-Fi radio/client link
   - router or local equipment
   - WAN/access connection
   - upstream/shared building segment
3. Treat an absent global IPv6 address plus absent IPv6 default route as
   evidence only of no usable native IPv6 on this client. It does not prove
   PPPoE, identify the ISP, or prove congestion.
4. If IPv6 is absent, ask for the contracted ISP/service name and router model
   or WAN status. Research IPoE requirements only from the ISP's current
   official documentation. State PPPoE versus IPoE as unverified until router
   or contract evidence establishes it.
5. Use RPM and the derived loaded round-trip time to assess bufferbloat. A high
   idle-to-loaded increase can explain poor interaction even when throughput is
   adequate.
6. Inspect traceroute hop 2. Classify a private, CGNAT, public, or nonresponsive
   hop, but compare it with the user's expected topology before saying a device
   is missing or unexpected.
7. Rank remedies by expected impact and evidence. Explicitly label a remedy
   `効果なし` when measurements rule it out. If Wi-Fi measurements and a
   controlled before/after test do not improve, say clearly that placement or
   channel changes are ineffective for the observed bottleneck.

## Report

Include these sections in the final diagnosis:

1. **Conclusion**: bottleneck and the decisive numbers, or “not yet
   identifiable” when required measurements are absent.
2. **Ranked actions**: highest expected impact first, with validation criteria.
3. **効果なし**: actions contradicted by the measurements.
4. **実測で裏付けられること**: claims directly supported by JSON values.
5. **推測**: plausible interpretations with their assumptions.
6. **未検証**: building equipment, access technology, ISP plan, router CPU, or
   other facts the tools cannot observe.

Never present a single Wi-Fi run as proof of building-wide congestion, router
CPU limits, or PPPoE/IPoE use.
